## 1. Correction: the first forward marks are due 2026-08-29, not 08-27

`HANDOFF-2026-08-23.md` (and the 08-22c handoff before it, and the memory entry) all said the
first 1w marks become due **2026-08-27**. That is wrong, and if you ran the marking command on
the 27th you got `0` with no way to tell why.

**Root cause:** the 08-22c handoff asserted "Session date is 2026-08-20". It is not. All 50
observations carry `session_date = 2026-08-22`. Verified today against the live database.

A mark is due when `session_date + horizon_days <= today`, so the real schedule is:

| horizon | first markable |
|---|---|
| **1w** | **2026-08-29** (tomorrow) |
| 1m | 2026-09-21 |
| 3m | 2026-11-20 |
| 6m | 2027-02-18 |

All four horizons return `due now: 0` today, and the 1w cutoff `2026-08-21` is one day short of
the session date.

**The generalisable lesson:** the date was carried across three handoffs and a memory entry
without anyone re-deriving it. It was asserted once, in prose, then quoted forward. **A date
computed from stored rows should be re-read from the rows, not copied from the last document
that mentioned it.**

Nothing is lost by the delay. Because the correction factors are computed over the window
`(session_date, as_of]` rather than inherited from fetch-time adjustment, **a mark taken late
produces the same numbers as a mark taken on time.**

## 6. Method notes from this session

- **Re-derive dates from data, never from the last document that stated them.** Section 1.
- **A mutation that reports PASS may not have run.** Three false PASSes in one session: a
  Git Bash `/tmp` vs Windows-Python `/tmp` mismatch meant the mutated file was never written; a
  syntax-error mutation; and a no-op mutation (`{} or {...}` — an empty dict is falsy). Assert
  the anchor was found AND `ast.parse` the result. A false PASS certifies the inverse of truth.
- **A test can pass without exercising what it names.** The explicit-reject-reason test passed a
  gate whose `failed_on` was already `None`, so it would have passed whether the rule existed or
  not. Only mutation caught it.
- **`gh pr merge --delete-branch` on the base of another PR auto-closes that PR**, and a closed
  PR whose base branch is gone can be neither reopened nor retargeted. Retarget dependents to
  `master` BEFORE merging their base.
- **Check what is already recorded before building provenance.** The gate-versioning item
  assumed cohorts could not be re-derived; `fundamentals_json` already stored the whole 185-key
  `.info`. The real gap was narrower — the pipeline *branch*, not the thresholds.
