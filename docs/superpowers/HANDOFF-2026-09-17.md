## 2. What happened, and the reasoning not in the code

### 2a. A PASS signature must be established before the data exists

The §1b check as written in 09-16b said "expect 10 rows, **all non-NULL**". Two independent
problems with reading that literally, both found before the scan ran:

**A NULL would have been undecidable.** `screen_price` reads `currentPrice` then
`regularMarketPrice` and returns `(None, None)` **by contract** if neither is present. Had the ETF
`.info` carried no price field, every row would be NULL for a reason unrelated to whether #61
reached the process — and there would have been no way to tell the two apart afterwards. Probing
`.info` in advance turned that into a decided question, and incidentally established that the
expected label differs from every priced row in the table's history (§1a).

**The check would have false-alarmed.** Rows at `stage_reached='universe'` — the three pre-`.info`
skips (`skipped_recommended_today`, `skipped_open_position`, `skipped_active_recommendation`) —
legitimately carry no price, because `.info` was never fetched for them. BND was exactly that on
09-16. A checker must encode the exclusion **the code actually implements**, not the headline
expectation. The verifier excuses `universe`-stage rows by stage and demands a source only from
rows that reached `.info`.

**The verifier was validated against a session known to carry the defect** before being trusted —
the §2a discipline from 09-16b. Run against 2026-09-16 it fails with exactly 9: the 9 rows that
reached `.info`, BND correctly excused, every price a float32 artifact bit-identical to
`tech_price`. A checker that has only ever passed is indistinguishable from one that matches
nothing.

### 2b. A mis-scoped denominator manufactured a regression that did not exist

Querying rows with empty `headlines_json` using `stage_reached != 'universe'` returned **9**, which
looked like a failure of the news chain that had shipped two days earlier. It was not.
**The news fetch sits *after* the fundamental gate**, so all 9 were `rejected_fundamental` rows
that never reached it. The correct predicate is `stage_reached NOT IN ('universe','fundamental')`,
which returns **0 on 09-17 and 0 on 09-16**; the broken one returns 9 on both.

**A number is only alarming relative to a baseline computed the same way.** Running the suspect
query against a known-good session is a two-second test that distinguishes "regression" from
"my query is wrong", and it should be the first move, not the last.

A second instance the same session, worth recording because the shape recurs: a diagnostic using
`getattr(cfg, 'twelve_data_api_key', '')` reported a wiped credential. `Config` has **no such
field** (that key is deliberately unwired — Twelve Data has no news endpoint), so the `getattr`
default made "attribute does not exist" indistinguishable from "attribute is empty" — precisely the
failure the probe was written to detect. **Fallback values that impersonate the failure mode** are
the same trap as NaN surviving `is None` and `.get("bidPrice", 0)` pricing a sell at give-it-away.
The project's rule — refuse hostile values at every boundary, never default them — applies to
throwaway diagnostics too, which is where it is easiest to skip.

### 2c. The four locks are a chain; you only ever see the first failing link

Verified in code rather than inferred, because the question "is `/resume` enough?" has a different
answer depending on what it is enough *for*:

1. **Guard 1** (`check_authorization`) runs **before `defer()`**. An empty allowlist denies
   everyone, so with `ALLOWED_DISCORD_USER_IDS` absent, **`/resume` alone changes nothing
   observable** — every Approve click still dies at the first check.
2. **Guard 2** (`trading_enabled`) runs inside `evaluate_trade`, which the approval path calls
   **unconditionally**. The `if self.config.dry_run:` branch sits *after* the decision
   (`bot.py:322`) and only skips the order-row INSERT. So the full guard table applies in a dry
   run, and a `HALTED` kill switch refuses simulated buys too. This is deliberate: the old path
   wrapped that check in `if not dry_run`, which meant the simulation was modelling a system
   without the brake.
3. **`_assert_live_execution`** at the sink demands `execution_mode == 'live'` **and**
   `dry_run is False`. `__post_init__` derives the second from the first, and `DRY_RUN` in the
   environment **fails startup**, so it must not be set by hand.

**Operational asymmetry:** `/resume` is durable, immediate and cross-process (DB state, and
`TRADING_ENABLED` cannot undo it). `EXECUTION_MODE` and `ALLOWED_DISCORD_USER_IDS` are env, read
at `Config()` construction, so both are inert until a **restart**. Note also that `/resume` is
sticky: running it to exercise a button means a later `EXECUTION_MODE=live` starts with the brake
already off.

### 2d. The Schwab token: half of it already renews itself, and the other half cannot

The token file holds **two** tokens, and conflating them is the whole confusion:

- **`access_token`, 30 minutes** (`expires_in: 1800`) — **already auto-renewed** by schwab-py on
  every call, with no human involved. Evidence from the live file: `expires_at` is **38.1 hours**
  after `creation_timestamp`, so it was rolled at 2026-09-17 14:16 UTC, mid-scan.
- **`refresh_token`, 7 days** — **cannot be extended.** Verified in `schwab-py`'s `auth.py`:
  `creation_timestamp` is captured once at login and written back verbatim on every token write
  (line 117), **never reset on a refresh**. So no amount of bot activity rolls the window. This is
  Schwab policy, not a library choice, and `auth.py:8` in this repo already said so.

Automating the browser login is technically possible and was **advised against**: it requires
storing full brokerage credentials plus an MFA bypass on this machine, replacing a credential that
is scoped and expires weekly with one that is neither; it breaks silently when the login page
changes, surfacing as "no trading today"; and it inverts the #51/#52 decision that the bot never
logs in. **The weekly expiry bounds the blast radius of a compromise of this host** — which
matters more than usual given a public repo and keys in `.env`. Recommended instead: a fixed
weekly login (e.g. Sunday evening), which makes the Tuesday warning a backstop rather than a
deadline.
