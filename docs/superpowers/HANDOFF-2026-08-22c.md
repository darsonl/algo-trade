## 2. What the 78% fix actually is

**The problem.** `pending_shadow_marks` required a `reference_price`, and only the 4
post-technical `_record_shadow` sites recorded one. 39 of 50 candidates in the acceptance scan
were rejected at the fundamental gate, carried no price, and could never be marked.

**The naive fix would have shipped a subtler bug.** Pricing the rejects from `.info` while
leaving the passers on `closes.iloc[-1]` puts two different quantities in one column:

| | source | fetched | adjusted? |
|---|---|---|---|
| `.info["currentPrice"]` | quote endpoint | during `partition_watchlist` | raw |
| `closes.iloc[-1]` | chart/history endpoint | after headlines + analyst | **auto-adjusted** |

A cohort comparison across those would measure provenance as much as outcome — the one thing
this subsystem exists to avoid.

**What shipped instead: one price, one policy, at every post-`.info` exit** —
`rejected_fundamental`, `skipped_quota_exhausted`, `rejected_signal`, `rejected_technical`,
`recommended`. The technical price still lives in `technicals_json`; it is simply not this
column. `reference_price_source` records provenance so the fallback is never silent.

**The backfill rewrote all 50 rows, not just the 39.** The 11 that already had a price carried
the technical-stage one; leaving them would have preserved exactly the confound above.

Verified on the live database:

```
observations 50, markable 50 (100%)   -- was 11 (22%)
  rejected_fundamental  n=39  markable=39
  rejected_signal       n= 7  markable=7
  rejected_technical    n= 2  markable=2
  recommended           n= 2  markable=2
  source: backfill:info.currentPrice   50
```

### Details that will look like details and are not

- **`screen_price` is TOTAL by contract.** It is passed as an *argument* to `_record_shadow`, so
  it runs **before** that wrapper's `try`. A raise would turn a genuine rejection into an
  `error` observation and could fire an ops alert. It refuses bools (`isinstance(True, int)` is
  True), NaN and infinity (both floats; NaN compares False to everything), strings, and
  non-positive values.
- **`previousClose` is deliberately NOT a fallback.** It is a different session, so substituting
  it silently moves the holding-period start and the return covers a window the benchmark does
  not.
- **`pending_shadow_marks` requires `reference_price > 0`**, not `IS NOT NULL`. Zero made a row
  eligible while guaranteeing `compute_return` returned None — a fetch per horizon and four
  permanently unusable marks.
- **Marking is now bounded** (`MAX_MARKS_PER_RUN=200`, `MARKING_TIME_BUDGET_S=120`, plus
  `ORDER BY`/`LIMIT`). It is serial with a 10s yfinance timeout per fetch and runs *before* the
  universe is built on a market-timed scan; this change multiplies its load ~4.5×. Skipped rows
  stay due, so a bound costs a delay, never a mark.

## 3. The external review that reshaped it

Codex reviewed the design before implementation and returned **NEEDS CHANGES**. Two of my four
claims were wrong, and I had them wrong in interesting ways:

- **The equivalence claim died.** I suspected a Saturday confound (market closed, so
  `currentPrice` trivially equals the last close). That theory was *also* wrong: yfinance 1.2.0
  `history()` **merges Yahoo's live row into the current daily bar**, so `closes.iloc[-1]` is
  not "the last completed bar" either. The real defect is provenance and adjustment, not timing.
- **The "selected forever" claim was overstated.** A zero price does not retry forever —
  `record_shadow_outcome` inserts a NULL-return row and `NOT EXISTS` then excludes it. It wastes
  four fetches. The policy conclusion survived; the mechanism was wrong.
- **The missingness objection was the one I missed entirely.** `skipped_quota_exhausted` has
  `.info` in hand, and quota exhaustion depends on scan order, day and provider budget — so
  leaving those rows unpriced makes *markability correlate with how a candidate exited*. That is
  what forced the scope past "fundamental rejects only".

**Operational note for next time:** the Codex runtime cannot resume a thread while its job is
running — a follow-up message becomes a second job that fails instantly with
`Task ... is still running`, and `SendMessage` still returns success. The first job then hung
(log frozen 24 min while reporting `running`). Check `codex-companion status <id>` **and log
growth**, not status alone. The fix that worked: cancel, then restart with everything in one
prompt.

## 6. Method notes worth keeping

- **The vacuous-test trap struck again, in a new form.** A mutation survived: deleting
  `ORDER BY` from `pending_shadow_marks` broke nothing, because `idx_shadow_obs_session` is on
  `(session_date, ticker)` and the index scan returns session-date order anyway. The test was
  confirming SQLite's index, not the clause. Fixed by inserting tickers in reverse alphabetical
  order within one session date so the two orders differ. **Generalised tell: a test can pass
  because of an index, a default, or a coincidence — mutate the thing it names.**
- **Run the tool against the real database, not only fixtures.** Two defects surfaced only that
  way this session: the report tracebacking on a database with no shadow tables, and the
  backfill tracebacking on one with no `reference_price_source`.
- **Commit before mutation-testing.** `git checkout <file>` on an uncommitted implementation
  discards the implementation, not the mutation.
