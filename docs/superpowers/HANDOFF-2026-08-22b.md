## 2. The methodology finding of this session

**Three of the four remaining tasks shipped with defects in the PLAN, and the same defect
shape appeared for the third time on this branch.**

Task 6's briefed tests called `queries.set_shadow_human_action` directly — a function that
shipped in **Task 4**. All three passed against untouched production code, and not one of them
imported `discord_bot.bot`, the only module the task changes. They would have survived deleting
the entire task.

That is the third instance here. Task 5's ETF test instrumented `get_universe`, a function the
ETF path never calls; a sibling test did the same the cycle before.

**The tell is identical every time: a test whose import list never names the module under
change.** It is now recorded in the plan file, in the ledger, and in memory. It is worth
promoting to a standing item in the pre-flight conflict scan rather than catching a fourth
time.

The compensating control used throughout this session was **mutation testing** — 20 mutations
across the four commits, each applied, run, and restored. It caught something a green bar could
not: `INSERT OR IGNORE` → `INSERT OR REPLACE` left every test passing, and chasing that gap is
what surfaced the split-adjustment hazard in §3.

One operational rule learned the hard way and now written into the plan: **commit before
mutating.** Restoring an *uncommitted* implementation with `git checkout <file>` discards the
implementation, not the mutation.

## 3. ⚠️ Two findings that need your ruling

Neither is a bug. Both are about what the instrument will be able to measure, which is a
question about the spec rather than the code.

### 3.1 The funnel cannot ask about the fundamental gate at all — and that is 78% of it

`pending_shadow_marks` requires `reference_price IS NOT NULL`. Only **4 of the 15**
`_record_shadow` call sites pass a reference price, and all four are post-technical — so that
filter silently means *"reached the technical stage"*.

**The acceptance scan measured the cost, and it is the dominant term:**

| outcome | n | can ever be marked? |
|---|---|---|
| `rejected_fundamental` | **39** | **no** — no price was ever captured |
| `rejected_signal` | 7 | yes |
| `rejected_technical` | 2 | yes |
| `recommended` | 2 | yes |

**39 of 50 — 78% of everything the pipeline saw — can never receive a forward mark.** The
funnel can tell you the fundamental gate rejects three quarters of the universe. It can never
tell you whether it was right to, because those candidates have no price to follow.

Given that the fundamental gate is one of the two gates the spec declared unbacktestable, this
is the single biggest limit on what forward recording will recover, and it is now a measured
number rather than an estimate.

Fixing it means capturing a price at the fundamental stage too — one extra quote per rejected
candidate per scan, ~39 per scan at today's rates. Cheap, but it is a spec change.

### 3.2 Splits corrupt `return_pct`, and the fix is a definition, not a patch

yfinance returns **back-adjusted** closes. The ticker's entry is `reference_price`, captured
live and unadjusted; its exit comes from adjusted history. **A 4:1 split inside the window reads
as a ~75% loss that never happened.** The benchmark leg is immune — both its ends come from the
same function, so the adjustment cancels.

Left unfixed on purpose and documented at the fetch site
(`research/outcomes.py::_close_on_or_before`). Using the session close as the entry would make
both ends consistent but would discard the intraday decision price — which is the price a human
would actually have transacted at. **That is a choice about what the metric means.**

Marks carry `as_of` and `price`, so any affected row can be recomputed once the call is made.

regardless of how far the candidate actually got, so `stage_reached` undercounts for errored

reads the funnel, not a defect. Left as-is deliberately.
