## 1. NaN reached SQLite as NULL, and nearly lost the data permanently

`scripts/mark_outcomes.py` was built, run for real, and immediately wrote **50 marks with NULL
`price` and NULL `return_pct`**.

yfinance returned a `2026-08-28` bar with `Close=NaN` — a placeholder for a session it has no
data for yet. **NaN is truthy, compares False to everything, and survives every `is None`
check.** It flowed `close_on_or_before` → `compute_return` → the INSERT, where **SQLite stored
it as NULL**.

That is exactly what `mark_due_outcomes`'s own docstring warns about:

> writing a NULL mark would convert one transient yfinance outage into permanently missing data
> with no way to retry it

Because the **row** existed, `pending_shadow_marks`'s `NOT EXISTS` excluded it. Those 50
observations could never have been marked again. The project's only outcome data was one
command away from being permanently lost, and the report would have shown `n=0` forever with
50 rows sitting in the table.

**The fix is only what the docstring already promised.** `close_on_or_before` says it "resolves
backwards to a **real bar**" — a NaN row is a session with no data, the same as a weekend for
this purpose. It now skips non-finite bars. `split_factor` had the trap in sharper form:
`if value:` is **True for NaN**, so one NaN in `Stock Splits` multiplied the factor to NaN and
took the whole mark with it. Both factor functions and both arithmetic helpers
(`compute_return`, `adjusted_entry`) now refuse non-finite values.

**The uncomfortable part, and the generalisable lesson:** `screen_price` has guarded NaN since
it shipped, and CLAUDE.md already spelled the trap out ("NaN compares False to everything").
The rule was applied at one boundary and not the other. **When a rule about hostile float
values is written down, apply it at every point external data enters — not only where it was
first noticed.**

Recovery: all 50 rows verified unusable (`price` AND `return_pct` NULL, zero usable), backed
up, deleted, re-marked. Backup at `algo_trade.db.bak-pre-nanpurge-*`.

## 2. The tool

```bash
.venv/Scripts/python.exe scripts/mark_outcomes.py            # take matured marks
.venv/Scripts/python.exe scripts/mark_outcomes.py --dry-run  # look only: no fetch, no write
.venv/Scripts/python.exe scripts/mark_outcomes.py --max 2000 --budget 3600   # drain a backlog
```

It exists for more than convenience. `MAX_MARKS_PER_RUN` / `MARKING_TIME_BUDGET_S` are sized for
a job running **in front of a market-timed scan**; run by hand that rationale is gone and the
bound becomes a hazard, because a run that stops at the cap and says nothing is
indistinguishable from one that finished. So it **re-asks what is still due after marking** —
re-queried, not inferred from the count, since a mark can also be skipped when its price cannot
be read.

**It defaults to doing the work**, unlike `backfill_screen_price.py` which defaults to preview.
That sibling *rewrites* existing rows; marking only appends and is idempotent.

## 2b. Backups: `cp` was never safe here (PR #42)

`scripts/backup_db.py` takes a rotated, verified snapshot. **Use it before anything
destructive**; do not use `cp`.

```bash
.venv/Scripts/python.exe scripts/backup_db.py            # keep newest 5, into backups/
.venv/Scripts/python.exe scripts/backup_db.py --keep 20
```

`get_connection` sets `journal_mode=WAL`, so a committed transaction lives in the `-wal`
sidecar until checkpointed — **copying the `.db` alone can omit committed rows** and yield a
snapshot that opens cleanly, passes an integrity check, and is quietly missing data. Every
ad-hoc backup taken by hand in this project before PR #42, including earlier the same day, used
`cp`. `sqlite3.Connection.backup()` reads through the WAL instead.

Three defects surfaced only by **running it against the real database**, none by fixtures:
same-second runs silently overwrote each other; the copy inherited WAL mode and grew
`-wal`/`-shm` siblings that rotation would orphan forever; and the collision suffix `-01`
sorted *before* the plain name (`-` is 0x2D, `.` is 0x2E), so rotation — which orders by name —
would have deleted the **newer** backup first. Separator is now `_` (0x5F).

## 6. Method notes worth keeping

- **Run the tool for real, against the real database.** The NaN bug was invisible to 1282
  passing tests, 5 killed mutations and a synthetic end-to-end run; it appeared on first contact
  with live yfinance data. The backup helper then produced three more defects the same way —
  same-second clobbering, leaked WAL sidecars, and a collision suffix that sorted backwards.
  **Four times in one session, running against reality found what fixtures could not.** Reading
  the actual output matters as much as running it.
- **A rule written down once is not a rule applied everywhere.** Section 1.
- **Re-derive dates from data, never from the last document that stated them.**
- **A mutation that reports PASS may not have run.** Three false PASSes in one session: a Git
  Bash `/tmp` vs Windows-Python `/tmp` mismatch, a syntax-error mutation, and a no-op mutation
  (`{} or {...}` — an empty dict is falsy). Assert the anchor was found AND `ast.parse` the
  result.
- **A test can pass without exercising what it names.** Only mutation caught it.
- **`gh pr merge --delete-branch` on the base of another PR auto-closes that PR**, and a closed
  PR whose base branch is gone can be neither reopened nor retargeted. Retarget dependents to
  `master` BEFORE merging their base.
- **Wait for CI.** #41 showed `MERGEABLE/UNSTABLE` — checks pending, not failing. Merging past
  that would have been merging blind.
