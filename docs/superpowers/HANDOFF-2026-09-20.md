## 2. What happened, and the reasoning not in the code

### 2a. The fix the last handoff asked for could not have worked, and the task XML says why

09-19 §3 item 3 proposed "a startup check that says so loudly." Two lines in
`scripts/algo_trade_task.xml` make that unreachable:

```
<MultipleInstancesPolicy>IgnoreNew</MultipleInstancesPolicy>
<ExecutionTimeLimit>PT0S</ExecutionTimeLimit>
```

`IgnoreNew` discards every trigger while a task instance is running — **including the next day's
20:00 occurrence**, not merely the 30-minute repeats, because the policy is a property of the task
rather than of one trigger. `PT0S` means *no limit*, not *zero seconds*, so Windows never reaps the
instance either. **A stuck process therefore suppresses its own replacement.** `main.py` never
starts, and a check at its head is dead code in precisely the scenario it was written for.

The 2026-09-18 log is the proof, and reading it correctly required knowing which lines mean what:

```
19:59:52  Discord bot ready as ATBot#8498      <- RESUME of the STUCK process
19:59:53  SchedulerAlreadyRunningError
20:00     (the task fired here and produced NOTHING)
21:20:28  Discord bot ready as ATBot#8498      <- another RESUME
21:26:27  Holding the PC awake ...             <- the first genuinely NEW process
21:26:27  Kill switch state at startup: HALTED
```

`Holding the PC awake` and `Kill switch state at startup` are the **only** startup-only lines.
`Discord bot ready` looks like one and is not — discord.py re-fires `on_ready` on every gateway
RESUME, 46 times in the 09-17 session. This is 09-18 §2c's lesson in a third costume: **an
intention and an event produce different log lines, and a line that merely looks like evidence is
worse than none.** A handoff read an arming line as an exit; here a resume line reads as a start.

So the deadman had to live **inside** the process. `process_watchdog.py` is a plain daemon
`threading.Thread`, and each of those words is load-bearing:

- **Not an APScheduler job.** APScheduler discarding its jobs *is* the failure being caught. A
  watchdog scheduled on it inherits the defect it exists to catch — the same reasoning that puts the
  kill switch at `_call_place_order` rather than at each caller.
- **Daemon.** A non-daemon watchdog thread would itself keep the interpreter alive at shutdown: the
  fix becoming the bug. Pinned by its own test, because nothing else would notice.
- **Waits on an `Event`, not `time.sleep`.** A sleeping host freezes this thread too, so it fires
  within one tick of **waking** — which is exactly the 09-17 shape, where both exits had already
  been discarded before the host came back.
- **Armed in `main()` before `bot.run()`, not in `on_ready`.** A process that never reaches
  `on_ready` — gateway never connects, channel check raises — is exactly as stuck as one that does,
  and `on_ready` has already demonstrated (09-18 §2b) that it can abandon its own tail partway
  through.

The deadline is `session_close + POST_SCAN_WINDOW_MIN + WATCHDOG_GRACE_MIN`, **not the close
alone**. A restart inside the approval window legitimately arms its exit at `last_scan + window`,
which with a late enough last scan lands after the bell. The window term is what makes firing a
**calendar fact rather than a judgement call**: past that instant, staying up was never something
the bot was told to do, so there is no false positive to protect against.

On firing it persists an ops alert **straight to the outbox table**, not via `bot.send_ops_alert` —
that is a coroutine on the very loop we have stopped assuming is healthy. The outbox is durable and
drains at the next scan start, so the operator sees it although the process is already gone. This
is the first time the outbox's design has actually been needed for its stated purpose. Then a
*bounded* graceful close, then `os._exit(1)` regardless: an unwritable database or a dead loop is a
reason to exit, not a reason to stay up.

### 2b. The unit tests could not see the defect, because they never let a clock produce the value

Every unit test passed a synthetic `timedelta(hours=8, minutes=27)`, which stringifies cleanly.
Driving the real watchdog in a real process printed this into the operator's only artifact:

```
outlived its deadline of ... by 8:15:00.001405 and was shut down
```

A real overdue interval is the **difference of two clock readings**, so it carries microseconds.
The tests were not wrong; they were fed values that could not exhibit the problem.

This is the volume gate again, in miniature: its tests used complete synthetic bars, so nothing saw
the partially-formed live one, and a gate that blocked 100% of candidates shipped. **When a value
comes from the outside world, a test that constructs it by hand is testing your idea of it.** The
fix truncates at the boundary where the value becomes operator-facing, and has its own test.

Verified end to end afterwards — real process, real `os._exit`, exit code 1, alert row durable with
`delivered_at` NULL. That run is what this handoff would cite if asked for proof, not the fact that
the unit tests are green.

measured case first on the dividend-floor precedent:

1. **`ETF_MAX_EXPENSE_RATIO` gates nothing** — it picks a warning colour in `embeds.py:96`.

   row, so the analyst is their only filter.
3. **`hold_system_awake()` does not prevent every sleep** — it blocks *idle* sleep only; a lid close
   or a user-initiated suspend goes straight through. The watchdog now bounds the *consequence* of
   such a sleep, which is a different thing from preventing it.
4. **The watchdog has never fired in production.** It is verified in a real process but on a
   synthetic deadline. Like #62, it is tested and unexercised — do not write it up as confirmed
   until a real incident or a deliberate suspend exercises it.
