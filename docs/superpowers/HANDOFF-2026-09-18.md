## 2. What happened, and the reasoning not in the code

### 2a. A one-shot exit and a 1-second grace cannot survive a host that sleeps

The log, which is the whole case:

```
2026-09-17 22:01:40  Last scheduled scan is done -- shutting down at 22:31
2026-09-18 06:58:53  (8h57m gap -- the host slept)
2026-09-18 06:59:07  post_scan_shutdown ... was missed by 8:27:27
2026-09-18 06:59:07  _shutdown_at_the_bell ... was missed by 2:59:07
```

`BackgroundScheduler()` (`main.py:1418`) is constructed with no `misfire_grace_time`, so
APScheduler's default of **one second** applied to both exits. A job that comes due while the host
is asleep is always later than that, so both were discarded and removed **without being called**.
`bot.close()` never ran.

`test_post_scan_exit.py`'s own docstring already records a 2026-09-14 sleep (08:33→20:06), and the
post-scan exit *was* the fix for it — exit early so the machine may sleep, rather than idle to the
bell. **That fix closed "sleeping during idle hours" and left "sleeping before the exit fires"
open.** A fix to a timing bug tends to move the vulnerable window rather than remove it, and the
second window is the one nobody writes a test for because the first one now has a test.

The grace change is **scoped to the two exits on purpose.** Scans keep the 1-second default:
`post_scan_shutdown_at` treats a run time in the past as "being processed, not waiting", and the
listener arms the exit on MISSED exactly as on EXECUTED — both depend on a missed scan never
re-running. A scan fired eight hours late would file observations under the wrong `session_date`
and re-open an approval window nobody is watching. `test_a_missed_scan_is_still_discarded` exists
to hold that line: **it was green before the change and stays green**, which is the only kind of
test that can prove a fix did not leak past its intended scope.

### 2b. The recovery code was sitting behind the line that threw

`on_ready` is not a startup hook. discord.py fires it again on every gateway RESUME — **46 times**
in that session, against 120 job adds and 16 raises. Each fire re-ran the scheduler setup:

- re-adding the scan jobs was **harmless** — stable IDs and `replace_existing=True` (`main.py:192`)
  make `configure_scheduler` idempotent, and it survived 46 calls cleanly
- `add_listener` has **no dedup**, so a 46th post-scan listener was stacked
- `scheduler.start()` **raised**, abandoning the rest of the handler

And the rest of the handler is the point. `main.py` already contained the recovery for exactly
this failure — the approval-window re-arm, commented *"Restarted inside the approval window: no
scan job will fire today, so no event will arm the exit. Arm it here."* It sits **after**
`scheduler.start()`. On a reconnect the raise came first, so **the repair for defect 2a was
unreachable from the only event that could have triggered it.** A latent idempotency bug disabled
the live fix for an unrelated one; neither would have been as bad alone.

Two disciplines in one function, one right and one wrong, is the thing to notice: whoever wrote
`replace_existing=True` understood the handler could run twice, and the `add_listener` and
`start()` calls a few lines below did not.

### 2c. A handoff asserted an exit it had not seen

The 09-17 handoff §4 ends "process exited on schedule ~22:31". The only log line near that time is
the one **arming** the exit at 22:01:40; there is no line recording it firing, and the process was
demonstrably alive 25 hours later. The claim was read off the arming line.

This is the same failure the 09-16 handoff corrected in itself ("stop the handoff asserting a SHA
it cannot know", `20f2909`), in a different costume. **An intention to exit and an exit produce
different log lines, and only one of them is evidence.** The next handoff that wants to claim a
clean exit should quote `Scans done and the approval window is over` — which 09-18 does have, at
22:31:33 — and ideally confirm no process survives it.

### 2d. The operator's own memory had rotted, in a way the repo had not

The persistent memory for this project claimed "Tasks 1–2 done, blocked on Python install" — true
in March, still being asserted in September, across 61 merged PRs and months of live running.
Acting on it would have meant re-scaffolding a finished project.

The cause is that the memory **duplicated** state the repo already tracked better: a task list that
had to be hand-updated to stay true, against a handoff chain that is rewritten every session by
construction. It has been rewritten to carry only what the repo cannot — the standing operational
facts, the `.env` reading rule, why browser login was rejected — and to point at
`docs/superpowers/HANDOFF-*.md` for anything dated. **Memory that restates a moving fact is worse
than no memory, because it is trusted.**
