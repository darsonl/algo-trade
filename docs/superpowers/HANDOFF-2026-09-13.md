## 2. A console wedged the scheduler and silently cost a scan

The first unattended night: the 09:30 ET ETF scan completed; **the 09:45 ET stock scan never
fired.** The evidence, all four parts of it:

* APScheduler logged **no `Running job` line at all** — it logs that *before* invoking the
  target, so the failure is upstream of `run_scan`, which would otherwise log
  `Starting scan...` or `Scan skipped` either way;
* **all** logging stopped at the instant the ETF scan ended;
* the process stayed alive another 21 minutes (`LastTaskResult 0xC000013A` was the manual stop);
* no Kernel-Power sleep event in the window — the machine was awake.

A Windows console has **QuickEdit Mode on by default**, and a stray text selection suspends
every write to it. The first thread to log then blocks forever **holding the `logging` module
lock**, so every other thread queues behind it — including the APScheduler executor. Process
alive + all logging stopped + job never submitted is exactly that signature.

**The code was verified not to be at fault**: two cron jobs two minutes apart, same
`configure_scheduler` path, stdout redirected to a file — both fired.

Fixed twice over, because the symptom and the hazard are different things:

* `build_log_handlers()` adds a `StreamHandler` **only when the stream is a terminal**. It tests
  `sys.stderr`, **not** `sys.stdout` — `logging.StreamHandler()` defaults to stderr, so gating
  on stdout would have been a no-op that read correctly.
* the task runs via `cmd` with stdout/stderr redirected to `logs/stdout.log`, so **no console
  exists to block**.

**This was never proven, only strongly inferred** — the process was gone by the time it was
diagnosed. The redirect removes the hazard class regardless.

## 3. Two more defects, both found by running it rather than testing it

**`Stop-ScheduledTask` orphans the python process.** The task action is
`cmd.exe /c python.exe main.py`, and stopping the task kills `cmd.exe` while leaving the python
grandchild alive — still holding the Discord connection, still running the old code. A restart
therefore produced *two* bots, one of them stale. **When stopping the bot by hand, check for
orphans:**

```powershell
Get-CimInstance Win32_Process -Filter "Name='python.exe'" |
  Where-Object { $_.CommandLine -like "*main.py*" }
```

**`StopAtDurationEnd` defaults to `true`.** The repeating trigger would have hard-killed the bot
9 hours in — 05:00 Taipei, *exactly* the winter close, racing its own graceful shutdown. Now
false. It was caught only because the task XML is now **exported from the live task** rather
than hand-written; the hand-written file never mentioned the setting at all.

**Lesson, consistent with the 08-30 handoff's four instances:** the deployment surface produced
three defects in one session and the test suite produced none of them. `Export-ScheduledTask`
after every change, and read what comes back.

## 4. What the bot does now

```
20:00 Taipei  task starts it      (= 08:00 EDT / 07:00 EST)
              not a session?      log + exit BEFORE touching Discord
              past today's close? log + exit
09:30 ET      ETF scan            (21:30 Taipei)
09:45 ET      stock scan          (21:45 Taipei)
16:00 ET      shuts itself down   (13:00 on half-days)
```

Task `\AlgoTrade`: daily 20:00 local, **repeating every 30 min for 9h** so a dead bot is back
within minutes. That repetition is safe only because of the `already_closed` state — otherwise
a repetition firing after the bell would start a process that idled until the next day.

Start is 20:00 **Taipei**, not ET, because Task Scheduler triggers are machine-local and Taipei
has no DST. The drift is 08:00 EDT → 07:00 EST: always *earlier* in ET terms, never past the
first scan. Same trap the scan times fell into before `SCAN_TIMEZONE` was set, pointed in the
harmless direction.

`SCAN_TIMES` is now **`09:45` only**. 15:30 ET is 03:30 Taipei and only ever fired on nights the
host happened to be awake; APScheduler has no catch-up, and a shadow observation cannot be
re-created at any price. One time that reliably runs beats two that mostly do not — the shadow
log's value is **session dates accumulated**, not scans per date.

### Scans skip non-trading days

`market_time.is_trading_session()` asks the real XNYS calendar, judged on the **Eastern** date
(21:00 ET Sunday is 01:00 UTC Monday). A `day_of_week='mon-fri'` trigger would have been simpler
and wrong: **Good Friday** is a market holiday but not a federal one, and Thanksgiving and July
4th observed all fall on weekdays. The Friday after Thanksgiving is the converse case — it
closes at 13:00 but **is** a session and must still scan. All four are pinned in tests against
live calendar values.

It **fails OPEN**, inverting this codebase's usual rule, deliberately. The kill switch and the
preflight table protect *capital*, so an unknown there must refuse. This guard protects *data
quality*, and a scan places no orders. A junk weekend row is identifiable by `session_date` and
deletable; a trading day lost to a flaky calendar lookup is gone for good.

`session_close_utc()` is read from the calendar, never assumed. **16:00 ET is not a constant**
(two half-days close at 13:00) and **not a constant in UTC** either (20:00 UTC in summer, 21:00
in winter), so pinning either would be wrong half the year.

The shutdown job deliberately does **not** call `.result()`, unlike the scan jobs beside it.
Both run on the scheduler thread, but a scan needs its outcome whereas this one asks the event
loop to stop — waiting on the coroutine that tears down the loop you are waiting through is how
you deadlock. Verified live with a 45-second fake close: `main()` returned, exit 0.

### tests/conftest.py is new and load-bearing

The trading-day guard made **~36 unrelated scan tests depend on the wall clock** — they all went
red the moment it landed, on a Sunday. One autouse fixture pins the calendar suite-wide. This is
the same principle the project already applies by threading an `instant` through every
time-dependent query: **the clock is not a test input.** Tests that *are* about the guard
override it locally and win, because the autouse fixture is applied first.

## 7. Method notes worth keeping

- **Read the log after the tool runs, not just the exit code.** §2 was found while verifying an
  unrelated cosmetic fix. 1320 tests passed for the entire time the scheduler was wedged.
- **`Export-ScheduledTask` after every change.** §3's second defect was invisible in the
  hand-written XML and obvious in the exported one.
- **Verify a diagnosis before acting on it.** The scheduler failure *looked* like a code bug;
  reproducing two cron jobs two minutes apart proved the code fine and moved the search to the
  environment. Guessing would have produced a confident fix to working code.
- **Re-derive state from the data.** "50 observations" was stale within a day — it is 60, and
  the extra 10 are a problem (§6.1). The 08-30 handoff makes this same point.
- **When a guard makes unrelated tests clock-dependent, fix it centrally.** Patching 36 tests
  would have "worked" and left a suite that passes Mon–Fri and fails at weekends.
- **Splitting commits means building the intermediate state and testing it.** Both commits in
  #44 touch the same three files; the halfway point only exists if you construct it. Verified:
  1339 at commit 1, 1352 at commit 2.
- **A guard's failure direction is a design decision, not a default.** This codebase fails
  closed almost everywhere; the trading-day guard fails open, and the reason it differs is
  written down beside it.
