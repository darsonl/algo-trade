## ⚠️ Environment — read before running anything

**Always use `.venv`.** It is Python 3.12, matching CI.

```bash
.venv/Scripts/python.exe -m pytest -q      # NOT `pytest`
.venv/Scripts/python.exe main.py           # NOT `python main.py`
```

System Python is **3.14** and the lock pins `pandas==2.2.3`, which has no cp314 wheel — the locked
stack is *physically uninstallable* outside the venv, and `pip install` there silently resolves
forward. **Never `pip install` into system Python for this project.**

**Regenerate the lock IN PLACE, over the existing `requirements.txt`:**

```bash
uv pip compile requirements.in --universal --python-version 3.11 -o requirements.txt
```

uv treats the output file as preferred pins and only moves what it must. Compiling to a *fresh*
path anchors nothing and floats every `>=` floor in `requirements.in`: measured this session, that
drifts **26 packages** and takes `openai` 2.41.1 → 3.1.0, a major bump that swaps its HTTP stack to
`httpx2`. This is now recorded in `requirements.in` itself.

## ⚠️ Arming — four independent locks, all currently engaged

| Mechanism | State | To arm |
|---|---|---|
| `DRY_RUN` | `true` | set `DRY_RUN=false` |
| kill-switch seed (`TRADING_ENABLED`) | `false` → seeds **HALTED** | `/resume` (needs `OPS_USER_IDS`) |
| `OPS_USER_IDS` | empty → **nobody can `/halt` or `/resume`** | set it, restart |
| **`ALLOWED_DISCORD_USER_IDS`** ⟵ **NEW** | empty → **nobody can approve anything** | set it (read at construction, so a restart suffices) |

The fourth is new this session and is the one that will surprise you: it is checked **before**
`defer()` and **regardless of `DRY_RUN`**, so with it unset every Approve click gets a private
"You are not authorized to approve trades." and nothing else happens.

It is deliberately **separate from `OPS_USER_IDS`**: halting is a safety action anyone trusted
should be able to take; spending money is not.

Order does not matter. `.venv/Scripts/python.exe scripts/check_ops_ids.py` still reports the ops
allowlist and switch state — it does **not** yet know about the approver allowlist, which is worth
adding.

## How the approval path works now

```
check_authorization        pure, BEFORE defer -> ephemeral reject, no broker calls
defer
-- approval gate --        one lock per loop, spans the WHOLE sequence
  quote, guard_snapshot    network, off the event loop
  BEGIN IMMEDIATE
    read day_notional + blocking orders
    evaluate_trade         12 guards, first rejection wins
    claim_recommendation_tx    expiry IN the SQL predicate
    INSERT the order row   <- the reservation IS the row
  COMMIT
  submit ONCE, classify_submission
-- release --
```

**The reservation is the row.** `BEGIN IMMEDIATE` takes the write lock *before* the reads, so two
processes serialise instead of both reading the same stale daily total (round-4 finding 8). The
`asyncio.Lock` is process-local and cannot stop a cross-ticker breach during an overlapping
restart; the transaction can. A rejection returns before the INSERT and rolls back.

**Only `submit_failed` releases capital and reopens the recommendation.** Everything ambiguous —
2xx-without-`Location`, 408/429/5xx, timeouts, anything unrecognised — is `submit_unknown` and
keeps reserving. `TradingHalted` classifies as `submit_failed` because we *know* nothing was
dispatched; it is the one failure where releasing is correct.

**The ledger owns ceilings, not positions.** `create_trade`/`upsert_position` still run on a
`submitted` outcome — the sell pass, `/positions`, `/stats` and the dupe check all read the
positions table. Removing that strands all four (I did, and caught it).

**Sells** run guards 1, 2, 3, 4, 5, 11, 12 only; the buy ceilings do not apply because selling
reduces exposure. Guard 12 revalidates the quantity against the broker. An ambiguous sell leaves
the **position open** — we do not know it sold.

## Conventions that cost something to rediscover

- **Day bucketing** = US market session via `market_session_bounds_utc()` as a range predicate —
  for the dupe guard and the analyst quota. **The order ceiling is the exception**: it buckets on
  `orders.intended_session_date`, because "entered Friday" and "trades Friday" are different
  claims. Never `'localtime'`, never bare UTC.
- **Order CRUD takes `conn`**, unlike the rest of `queries.py`, so cap-check and reservation are
  one transaction. `claim_recommendation_tx` follows the same rule for the same reason — a
  `db_path`-taking claim opens a second connection that blocks on our own write lock.
- **Terminal statuses are an allowlist**, never a denylist — Schwab's enum has 21 members
  including a literal `UNKNOWN`, and can gain more. Applies to `TERMINAL_ORDER_STATUSES` (ours)
  and `TERMINAL_BROKER_STATUSES` (theirs).
- **`None` and `[]` are different inputs** everywhere broker data flows. `None` = the read failed;
  `[]` = it succeeded and there is nothing. `BrokerSnapshot.readable` encodes it, guard 5 enforces
  it.
- **`CREATE TABLE IF NOT EXISTS` does nothing on an existing table.** Every new *column* needs the
  `ALTER TABLE` idiom, and a new **index over a new column must be created AFTER the ALTER** — put
  it in the schema block and it raises "no such column" on every pre-existing database.
- **Tests reaching Schwab must pin `dry_run=True`** regardless of `.env`.
- schwab-py is **1.5.1**. `schwab.Client` does NOT exist; it is `schwab.client.Client`.

### Do not "simplify" these back

- **The submission gate must not become a `threading.RLock`** — reentrant per thread, and all
  coroutines share the loop thread, so it provides *no* exclusion while looking correct.
- **Both gates must stay one lock per loop.** A module-level `asyncio.Lock` binds to the first loop
  that *contends* on it. `acquire()`'s uncontended fast path hides this from every test that never
  blocks — so both gate tests **contend**, on two loops.
- **Quote parsing must keep having no defaults.** `.get("bidPrice", 0)` on an error body prices a
  sell at give-it-away.
- **Guard 1 stays first** (rejection messages are a side channel) and **guard 5 stays before
  8–11** — verified by mutation: removing guard 5 leaves no clean refusal at all, only a
  `TypeError`.
- **Submission must never be retried.** No idempotency key exists; a retry is a second real order.
- **`intended_session_date` must not go back to a `submitted_at` range.**
- **The approval path must keep pricing from the quote the guards saw.** Fetching a second quote at
  submission time is how the checked price and the sent price come apart.

### Testing traps hit this session

- **A test that passes on first write has proven nothing.** Every load-bearing claim here was
  mutation-checked: the Good Friday and early-close tests were run against naive implementations
  and confirmed to kill them; guard 5 was removed and shown to leave only a crash. One existing
  test was found passing **by coincidence** — it backdated `submitted_at` with a raw `UPDATE` and
  only agreed because the session date happened to match on the day it ran.
- **`db_path=":memory:"` means a fresh empty database per connection.** Harmless until something
  reads durable state.
- **Patching the source module misses a `from x import y` binding.** `bot.py` binds
  `_call_place_order` at import, so `patch("schwab_client.orders._call_place_order")` does nothing
  — patch `discord_bot.bot._call_place_order`.
- **`quote=None` is a meaningful argument.** A `quote or default` helper silently substitutes the
  default, and the guard-4 test then passes while testing nothing. Use a sentinel.
- **`close_position` sets `status='closed'`; it does not delete.** A helper selecting every row
  never observes a close.
- **Beware backticks inside `python -c "..."` from bash.** Command substitution ate three
  identifiers out of CLAUDE.md this session and the script still printed "ok". Use a heredoc or a
  real file, then grep for what you just wrote.
- **When a rewrite obsoletes tests, check what coverage is leaving.** Roughly 30 tests were
  retired this session because they mocked `queries` wholesale and asserted call shapes — they
  described the old implementation, not behaviour. Their behaviours were re-established against a
  real database first (`test_approval_ledger.py`, `test_sell_approval_ledger.py`), and the
  double-click idempotency test was *ported* rather than dropped.

### GitHub workflow quirks

- `gh pr edit --base` fails on this PAT (needs `read:org`). Use
  `gh api -X PATCH repos/<owner>/<repo>/pulls/<n> -f base=master`.
- **Retargeting a PR does not trigger CI** — a base change emits `pull_request: edited`, not a
  default activity type. Close+reopen via the API emits `reopened`, which is.
- `.github/workflows/ci.yml` only runs for PRs targeting `master`, so a **stacked PR gets no CI**
  until retargeted. Every PR this session branched from `master` directly and got CI immediately.
